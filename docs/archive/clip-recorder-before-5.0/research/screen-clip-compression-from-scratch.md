# Change-driven hybrid coding keeps screen text exact

*Research report, compiled 2026-11-23 from published literature only. No local measurements were taken and no codec was assumed in advance.*

## Abstract

The published evidence points to one design as the best answer for recording application windows on Windows with exactly readable text, a small file and a light load on the machine. Capture the window as a GPU texture only when it changes, find the pixels that really changed, and code those regions with a fast lossless coder that predicts from the previous frame. Use lossy video coding only for regions that change constantly, and re-send those regions losslessly once they stop changing. This is the design every mature remote-display system converged on: RDP mixed mode, Citrix Thinwire, PCoIP, VMware Blast and TurboVNC. In the one published desktop-capture measurement, a trivial inter-frame lossless coder followed by zstd reached about **112:1 on a single thread**. That beat lossless x264 (about 83:1 on 16 threads, 2.6x slower) and FFV1 (about 22:1) ([1](https://ffmpeg.org/pipermail/ffmpeg-devel/2022-June/297402.html)). Temporal redundancy is the largest single lever. Inter-frame coders beat intra-only coders by **4x to 40x** on screen content, while codec generation or entropy-coder effort moves results only by tens of percent. Where a standard video file is required at record time, the next best options are lossless inter-frame H.264/HEVC in RGB or 4:4:4. NVENC gives the lowest CPU cost and x264 qp 0 the better ratio. When "readable" is enough and "exact" is not, a lossy codec with screen-content tools in 4:4:4 at constant quality is next. The decisive negative finding is that ordinary 4:2:0 lossy video damages text: Microsoft calls the effect a "halo" and built AVC444 to avoid it ([2](https://techcommunity.microsoft.com/t5/microsoft-security-and/remote-desktop-protocol-rdp-10-avc-h-264-improvements-in-windows/ba-p/249588)). OCR is a poor instrument for proving fidelity. It stays flat at 0-2 errors while cropped SSIM falls from 0.97 to 0.84 ([3](https://dev.to/yue_shu_c621a4a637f22396f/ocr-couldnt-tell-720p-lecture-text-from-1080p-a-cropped-ssim-could-4njo)). Exact-pixel and full-reference metrics on text crops should replace it, with OCR kept only as a floor check.

## Method: six literature sweeps, graded by source strength

The synthesis draws on six research notes compiled on 2026-11-23. Each note covers one family of techniques. The six families are lossy codecs and hardware encoders with screen-content tools; lossless video codecs; lossless image codecs and general-purpose compressors with delta coding; remote-display and hybrid content-adaptive protocols; the cost of the Windows capture pipeline; and OCR as a measure of text fidelity. Sources are standards and specifications (RFC 6143, RFC 9043, MS-RDPEGFX), peer-reviewed papers (APSIPA, IEEE TCSVT, SPIE, PLoS ONE, USENIX), vendor documentation (NVIDIA, Intel, AMD, Microsoft, Citrix, VMware), open-source code and commit logs (OBS, libaom, x265, SVT-AV1, libyuv), and community benchmarks (Doom9, TASVideos, ffmpeg-devel). The notes tagged each claim by strength. This report keeps that distinction. Numbers from forums and vendors are labelled as such. Claims the notes marked as unverified general knowledge are left out. Ratios not printed in a source but computed from its published sizes are marked as derived. No source compares all families on one corpus of real Windows desktop clips. Cross-family comparisons are therefore syntheses, not measurements, and the Limitations section states where that matters.

## Temporal redundancy outweighs every other coding choice

The strongest pattern in the literature is that, on screen content, whether a coder uses the previous frame matters more than which codec it is. On a Full-HD desktop capture of 208 GB uncompressed rgb24, lossless `libx264rgb -preset veryslow -qp 0` with GOP 32 produced **2.51 GB (about 83:1)** on 16 threads. FFV1, which is intra-only, produced **9.43 GB (about 22:1)**, 3.8x larger. A single-threaded inter-frame coder modelled on QOI followed by zstd level 8 produced **1.86 GB (about 112:1)** in 471 time units, against x264's 1218 ([1](https://ffmpeg.org/pipermail/ffmpeg-devel/2022-June/297402.html)). The source is one self-reported post with unpublished data, and the time unit is not stated. Every other data point agrees in direction. An FFV1 maintainer replied that FFV1 "does not do inter-frame decorrelation" and does poorly where "> 95% of the frame stays exactly the same" ([4](https://ffmpeg.org/pipermail/ffmpeg-devel/2022-June/297414.html)). On a GBA emulator dump, UtVideo needed 688 MiB, x264 qp 0 needed 58.6 MiB and ZMBV needed 43.5 MiB: 11.7x and 15.8x smaller than the intra-only codec. On a second emulator dump, the derived ratios were about 246:1 for x264 qp 0, 80:1 for CamStudio gzip-9, 17:1 for Lagarith and 6.3:1 for UtVideo ([5](https://tasvideos.org/Forum/Posts/302353)). MSU's own screen-capture codec page reports a "significant advantage of codecs which use delta-frames" ([6](https://compression.ru/video/ls-codec/screen_capture_codec_en.html)). On natural camera video the effect almost disappears: x265 lossless at GOP 1 and GOP 25 gave ratios of 2.44 and 2.46 ([7](https://forum.doom9.org/showthread.php?p=1954743)). Static screens are the regime where temporal prediction pays off, and it pays off by an order of magnitude.

The same logic sets the ceiling for per-frame image coding. Lossless still-image coding of web screenshots plateaus near **7.6-8.3% of raw size** (libpng and QOI). Game screenshots plateau near **20-25%** ([8](https://qoiformat.org/benchmark/)). That is roughly 4-13:1, far below the 83-246:1 that inter-frame coders reach on screen video. An image codec helps only when it codes changed regions rather than whole frames.

## Lossy codecs: screen-content tools beat codec generation, but 4:2:0 breaks text

Controlled reference-software studies measure large gains from the screen-content coding (SCC) tools. On the "text and graphics with motion" (TGM) class, closest to application windows, HEVC SCC saves **64.0% / 55.2% / 49.6%** BD-rate on RGB content against HEVC RExt (all-intra, random-access and low-delay configurations). Against AVC High 4:4:4 it saves **85.9% / 79.8% / 77.2%**. Gains on camera and animation content are about zero ([9](https://www.cambridge.org/core/services/aop-cambridge-core/content/view/E12DCF69B0A59DD269EFE14CD1AFBFBE/S2048770315000116a.pdf/overview-of-hevc-extensions-on-screen-content-coding.pdf)). Formal verification tests confirmed **60-90% savings versus AVC and 40-80% versus HEVC** without SCC ([10](https://www.microsoft.com/en-us/research/?p=798757)). VVC's SCC tool set (transform-skip residual coding, BDPCM, IBC, ACT, palette) saves a further **19-25% over HEVC-SCC** on 4:2:0 screen content ([11](https://www.microsoft.com/en-us/research/?p=798274)). Ablation identifies intra block copy (IBC) as the largest contributor and palette as the second. Integer motion vectors add 3-4% on TGM. ACT helps only RGB lossy coding ([9](https://www.cambridge.org/core/services/aop-cambridge-core/content/view/E12DCF69B0A59DD269EFE14CD1AFBFBE/S2048770315000116a.pdf/overview-of-hevc-extensions-on-screen-content-coding.pdf)). For comparison, the gap between fast and reference-quality encoders on general content is +98% BD-rate for x264 medium and +53% for x265 medium against HM ([12](https://www.cambridge.org/core/services/aop-cambridge-core/content/view/C1BEFBC1983E06BE4D67B239AC0F26A4/S2048770319000234a.pdf/a-comprehensive-video-codec-comparison.pdf)). On text, switching on SCC tools is worth about as much as a full codec generation.

Practical encoders expose only part of this. libaom forces palette and IntraBC with `--tune-content=screen` and measures **-10.8% PSNR BD-rate** on screen key frames ([13](https://aomedia.googlesource.com/aom/+/2a273eef9962296f8de0f449ac21776b2e372a6f%5E%21/)). Its v3.5.0 changelog reports 15% gains for real-time screen content at speed 10, plus 7.5% from a screen-specific rate-control mode ([14](https://aomedia.googlesource.com/aom/+/refs/tags/v3.5.0/CHANGELOG?autodive=0)). x265 4.0 added `--scc` for IBC search only. It is off by default, needs a special build, and has no palette or ACT ([15](https://x265.readthedocs.io/en/master/cli.html), [16](https://mailman.videolan.org/pipermail/x265-devel/2024-September/013940.html)). SVT-AV1 has `--scm` with off, on and content-adaptive modes ([17](https://gitlab.com/AOMediaCodec/SVT-AV1/-/raw/master/Docs/Parameters.md)). AV1 has a structural limit for recordings: IntraBC works **only in intra frames**, and enabling it turns off all loop filters ([18](https://arxiv.org/pdf/2008.06091)). In a mostly static window recording, AV1's text-copy tool helps keyframes only, while HEVC and VVC IBC is unified with inter prediction and works in every frame ([9](https://www.cambridge.org/core/services/aop-cambridge-core/content/view/E12DCF69B0A59DD269EFE14CD1AFBFBE/S2048770315000116a.pdf/overview-of-hevc-extensions-on-screen-content-coding.pdf)). The tools also cost complexity. One comparison measured encode time on the screen/mixed-content class relative to HM. In the max-efficiency configuration the ratios were 0.004 for x264 medium, 0.01 for x265 medium, 3.18 for AV1 cpu-used=0 and 6.34 for VTM ([12](https://www.cambridge.org/core/services/aop-cambridge-core/content/view/C1BEFBC1983E06BE4D67B239AC0F26A4/S2048770319000234a.pdf/a-comprehensive-video-codec-comparison.pdf)). The same study found that linear efficiency gains cost exponential complexity (R² = 0.97). Reference-quality SCC encoders are therefore far too slow for real-time capture on a modest CPU.

Chroma subsampling is the failure mode that matters most for text. Microsoft introduced AVC444 in RDP because "text shows a halo effect with typical implementations of AVC/H.264", caused by 4:2:0 ([2](https://techcommunity.microsoft.com/t5/microsoft-security-and/remote-desktop-protocol-rdp-10-avc-h-264-improvements-in-windows/ba-p/249588)). AVC444 sends two 4:2:0 streams, a luma main view and a chroma auxiliary view, from one encoder, and recombines them into 4:4:4 ([19](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-rdpegfx/8131c1bc-1af8-4907-a05a-f72f4581160f)). Consumer testing likewise finds 4:2:0 most damaging for "text atop a flat color" ([20](https://www.rtings.com/tv/learn/chroma-subsampling)). In the only screen-lesson encode test with crops, x264 CRF 23 kept **SSIM 0.9993 on black code text but 0.924 on red text** in the same frame ([3](https://dev.to/yue_shu_c621a4a637f22396f/ocr-couldnt-tell-720p-lecture-text-from-1080p-a-cropped-ssim-could-4njo)). Coloured text and ClearType fringes lose the most. Text-exact lossy coding therefore requires 4:4:4 or RGB. The SCC gains are largest in exactly that format ([11](https://www.microsoft.com/en-us/research/?p=798274)).

Hardware encoders shift CPU load to fixed-function silicon but narrow the format choices. NVENC is the only family with documented 4:4:4 and lossless encode. H.264 has both on every generation from Maxwell 1 to Blackwell, but 4:4:4 is "CAVLC only". HEVC has both from Pascal. NVENC AV1 is 4:2:0 only ([21](https://docs.nvidia.com/video-technologies/video-codec-sdk/13.0/nvenc-application-note/index.html)). Per-engine throughput at 1080p is **910 fps (H.264 P1) to 1090 fps (AV1 P1)** on Ada ([21](https://docs.nvidia.com/video-technologies/video-codec-sdk/13.0/nvenc-application-note/index.html)). A forum report says NVDEC cannot decode the H.264 4:4:4 that NVENC produces, though HEVC 4:4:4 decodes ([22](https://forums.developer.nvidia.com/t/nvdec-not-supporting-h-264-4-4-4-when-nvenc-does/157198)). Intel oneVPL lists HEVC 4:4:4 encode with SCC for 11th-13th gen Core ([23](https://www.intel.com/content/www/us/en/docs/onevpl/developer-reference-media-intel-hardware/1-1/features-and-formats.html)). FFmpeg exposes palette and IntraBC for Intel AV1 encode ([24](https://ffmpeg.org/pipermail/ffmpeg-devel/2024-September/333792.html)). AMD AMF shows no evidence of 4:4:4 or lossless encode; its 4:4:4 support sits in the colour converter only ([25](https://emby.media/learn/articles/hardware-acceleration/generations/amd/Hardware-AMD-VCN-Generations.html)). The inbox Media Foundation H.264 MFT takes 4:2:0 or 4:2:2 input only ([26](https://learn.microsoft.com/en-ie/Windows/Win32/medfound/h-264-video-encoder)). Citrix documents that its "lossless text is not compatible with NVENC hardware encoding" ([27](https://docs.citrix.com/en-us/citrix-virtual-apps-desktops/policies/reference/ica-policy-settings/graphics-policy-settings.html)). Exact text from a hardware encoder therefore requires NVENC lossless or 4:4:4, or Intel HEVC 4:4:4 where the CPU generation supports it.

## Lossless video codecs split into fast-but-big and small-but-temporal

Among lossless video codecs, intra-only designs (UtVideo, MagicYUV, HuffYUV/FFVHuff, Lagarith, FFV1) give the lowest CPU per frame and the simplest random access. They pay heavily in size on screens. Inter-frame designs (x264 qp 0, ZMBV, TSCC, MSU SCLC, ScreenPressor) are 5-40x smaller on screen-like content ([5](https://tasvideos.org/Forum/Posts/302353)). FFV1 is the strongest intra-only coder for ratio. In MSU's 2007 study it was "almost as good as YULS, while being much faster" in RGB24, at 3.30:1 and 6.31 4CIF fps for FFV1 Max ([28](https://www.compression.ru/video/codec_comparison/pdf/msu_lossless_codecs_comparison_2007_eng.pdf)). It is an open standard with slice-level threading ([29](https://www.rfc-editor.org/rfc/rfc9043)). Without temporal prediction, though, it lost 3.8x to x264 on desktop content ([1](https://ffmpeg.org/pipermail/ffmpeg-devel/2022-June/297402.html)). On CPU, the forum measurements are consistent. On 1080p60 on an 8-core FX-8320, UtVideo ran at **141 fps using 49-57% CPU** and x264 qp 0 ultrafast at **131 fps using 98%**. Single-threaded HuffYUV ran at 43.7 fps using 15% ([30](https://forum.doom9.org/showthread.php?t=165745)). On an i9-11900K, UtVideo encoded SD 10-bit at 832 fps using 34-38% CPU ([31](https://forum.doom9.org/showthread.php?p=2000869)). These are natural-video clips, and on static screens inter-frame coders also get cheaper, because unchanged blocks cost almost nothing. ZMBV encoded at about 1600 fps on the emulator dump ([5](https://tasvideos.org/Forum/Posts/302353)).

Dedicated screen codecs show how simple the winning mechanism is. ZMBV codes delta frames whose blocks are "either copied from the previous frame or XOR'ed with some block from the previous frame", then applies zlib ([32](https://wiki.multimedia.cx/index.php/DosBox_Capture_Codec)). TSCC is RLE plus zlib for sequences that "do not change much from frame to frame" ([33](https://wiki.multimedia.cx/index.php/TechSmith_Screen_Capture_Codec)). ScreenPressor's vendor claims "300x lossless compression at 300+ frames per second", with chart-only evidence ([34](https://infognition.com/ScreenPressor)). These codecs are legacy, Video for Windows or proprietary, which limits them as targets. Their design is exactly what the hybrid approach below generalises.

Bit-exactness also depends on colour handling, not just on the "lossless" label. FFV1 codes RGB through the reversible JPEG 2000 RCT ([29](https://www.rfc-editor.org/rfc/rfc9043)). MagicYUV is "bit-by-bit identical" in its RGB modes ([35](https://magicyuv.com/)). UtVideo has native RGB formats ([36](https://en.wikipedia.org/wiki/Ut_Video_Codec_Suite)). The 2022 desktop test used `libx264rgb` with rgb24 ([1](https://ffmpeg.org/pipermail/ffmpeg-devel/2022-June/297402.html)). Converting captured BGRA to YUV 4:2:0 before a "lossless" encode is lossy overall. HEVC SCC also improves lossless coding, by **48.0% / 30.2% / 29.2%** on RGB TGM versus RExt ([9](https://www.cambridge.org/core/services/aop-cambridge-core/content/view/E12DCF69B0A59DD269EFE14CD1AFBFBE/S2048770315000116a.pdf/overview-of-hevc-extensions-on-screen-content-coding.pdf)). Other SCC lossless figures are about 40%, 33% and 32% ([37](https://www.microsoft.com/en-us/research/?p=798826)). No production encoder was found that ships these lossless SCC gains in real time. Lossless x265 and AV1 are reported as very slow: "2 days" for a 2-hour SD tape, and AV1 lossless "basically useless" for speed. They also show no ratio advantage on camera content (aom-av1 447 vs x264 445 Mb/s) ([31](https://forum.doom9.org/showthread.php?p=2000869)). For lossless hardware encoding, NVENC offers a lossless tuning mode ([38](https://docs.nvidia.com/video-technologies/video-codec-sdk/13.1/nvenc-video-encoder-api-prog-guide/index.html)). The only ratio datum is a forum test on video, where NVENC H.264 lossless was **8% larger than x264 ultrafast lossless and about 40% larger than x264 medium** ([7](https://forum.doom9.org/showthread.php?p=1954743)).

## Image codecs and compressors: fast predictors plus zstd fit the real-time budget

If changed regions are coded as images, speed sets the menu. Recording 1080p at 30 fps means 62 megapixels per second, or 249 MB/s of raw BGRA. On web screenshots, QOI encodes at **310.6 MP/s** single-threaded for 8.3% of raw size. libpng manages only 14.8 MP/s for 7.6% ([8](https://qoiformat.org/benchmark/)). fpnge runs at 180-800 MP/s per core ([39](https://github.com/veluca93/fpnge)). fpng compresses about 23x faster than libpng ([40](https://github.com/richgel999/fpng)). libjxl's lowest effort reached 427 MP/s on photos while staying 32.5% smaller than QOI ([41](https://cloudinary.com/blog/jpeg-xl-and-the-pareto-front)). The densest formats are too slow for capture. On the QOIR suite, JPEG XL effort 7 is 39% smaller than QOIR but about 330x slower to encode, and WebP lossless is 35% smaller but about 67x slower ([42](https://github.com/nigeltao/qoir)). On artificial "illustration" images, FLIF (3.39 bpp) and JPEG XL (3.47 bpp) lead, ahead of WebP 2 (3.62), WebP lossless (4.29) and zopfli-optimised PNG (4.63). JPEG-LS (6.99) and lossless AVIF (8.20) are 50-77% larger than PNG ([43](https://arxiv.org/pdf/2108.02557)). That rules out lossless AVIF and JPEG-LS for screen content. WebP lossless at its fastest setting (`-q 0 -m 1`) was 35% smaller than libpng on a chart image and encoded 2.75x faster. Its encoder used 25-32 MiB of memory against 10-19 MiB for libpng ([44](https://developers.google.com/speed/webp/docs/webp_lossless_alpha_study)). JPEG XL memory is a caution. One 91 MP image at effort 1 needed 289 MB in v0.10, down from 821 MB in v0.9 ([41](https://cloudinary.com/blog/jpeg-xl-and-the-pareto-front)).

General-purpose compressors are fast enough but need a predictor. On the Silesia corpus, **zstd -1 compresses at 411 MB/s** with 1351 MB/s decode, LZ4 at 550 MB/s, and zlib -1 at only 89 MB/s for a slightly worse ratio ([45](https://github.com/inikep/lzbench)). Run directly on raw pixels, zstd output is **54% larger** than with a PNG-style filter in front; for LZ4 the penalty is 17%. The combination "PNG filter + zstd" was 10% smaller than libpng and about 23x faster ([42](https://github.com/nigeltao/qoir)). For temporal prediction, zstd can use the previous data as a reference. `--patch-from` raises the dictionary limit to 2 GB and runs at fast levels, though it was measured on source tarballs, not images ([46](https://github.com/facebook/zstd/wiki/Zstandard-as-a-patching-engine)). `--long` defaults to a 128 MiB window at the cost of matching decoder memory ([47](https://android.googlesource.com/platform/external/zstd/+/refs/heads/main-kernel/programs/zstd.1.md)). LZ4 dictionaries use only the last 64 KB ([48](https://raw.githubusercontent.com/lz4/lz4/dev/README.md)). That is too short to see a whole previous frame, so the previous frame must be subtracted or XORed explicitly before LZ4. Research screen-image coders such as Soft Context Formation sit 0.44 bpp below VVC ([49](https://arxiv.org/abs/2312.14491)). They mark a density ceiling, not a practical option.

## Remote-display systems converged on hybrid, build-to-lossless coding

Every mature remote-display protocol classifies screen regions and gives text its own lossless path. Microsoft reports that "approximately 80% of the graphics data for a remote session is text". Its default mixed mode sends text through a text-optimised codec and images and video through H.264. Full-screen video encoding "performs worse than mixed-mode encoding when the screen content is largely text based" ([50](https://learn.microsoft.com/en-us/azure/virtual-desktop/graphics-encoding)). RDP's ClearCodec is a layered lossless or near-lossless codec ([51](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-rdpegfx/23253264-20f7-4a85-b6b4-023ca955cb3f)). Citrix Thinwire sends text, simple images and solid colours losslessly, photos as JPEG, and only "actively changing regions" through H.264, H.265 or AV1 4:2:0. Its build-to-lossless mode sharpens to pixel-exact once activity stops ([52](https://docs.citrix.com/en-us/citrix-virtual-apps-desktops/graphics/thinwire/thinwire-selective-encoder)). On a LAN, PCoIP "always displays text using lossless compression" ([53](https://docs.vmware.com/en/VMware-Horizon/2006/horizon-remote-desktop-features/GUID-FB9598F4-EBBD-4CFF-B24E-CF9D18E729CD.html)). VMware Blast switches between JPG/PNG or Blast Codec and H.264 by content type and offers a build-to-PNG option ([54](https://techzone.vmware.com/resource/vmware-blast-extreme-optimization-guide)).

TurboVNC documents its classifier and its costs most openly, and both are cheap. Each changed rectangle is split into solid fills, two-colour bitmaps, indexed-palette subrectangles and many-colour regions. A subrectangle counts as palette when its unique colours number at most its size divided by 96. Zlib level 9 "uses approximately twice as much CPU time and only achieves about 10% better average compression for 2D applications" than level 1. TurboVNC removed TightVNC's "CPU-hungry smoothness detection" and kept plain colour counting. Its interframe comparison checks updates against a stored framebuffer copy in 256x256 blocks to drop redundant redraws. After an idle timeout, Automatic Lossless Refresh sends a "mathematically lossless copy" of regions that were lossily coded ([55](https://rawcdn.githack.com/TurboVNC/turbovnc/main/doc/index.html)). Independent measurements support the hybrid approach. In a 2018 PLoS ONE study, the hybrid protocols RDP and ICA gave "the best trade-off between bitrate and quality". RDP stayed under 1 Mb/s for office and web work. TeamViewer, which codes the screen as lossy video, fell **below 25 dB PSNR** on dynamic desktops, with median MOS 3 on office work ([56](https://pmc.ncbi.nlm.nih.gov/articles/PMC6320061/)). An earlier USENIX study found that compression mattered more than caching ([57](https://www.usenix.org/legacy/event/usenix02/full_papers/yang/yang_html/index.html)). One caution applies: RDP and ICA partly gain by remoting drawing commands, and a pixel recorder cannot do that. The transferable lessons are dirty-region coding, colour-count classification, a lossless palette path, low-effort entropy coding and lossless refresh. None of these depends on command remoting.

## The Windows capture pipeline costs little if frames stay on the GPU

Capture itself is not the bottleneck. Windows.Graphics.Capture (WGC) captures "a display or application window" into a BGRA (or FP16 on HDR) GPU texture ([58](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/screen-capture)). Each frame carries a QPC timestamp ("the compositor rendered the frame") and `DirtyRegions` ([59](https://learn.microsoft.com/en-us/uwp/api/windows.graphics.capture.direct3d11captureframe)). The session can hide the border and the cursor, and Windows 11 24H2 adds `MinUpdateInterval`, which is undocumented ([60](https://learn.microsoft.com/en-us/uwp/api/windows.graphics.capture.graphicscapturesession), [61](https://learn.microsoft.com/en-us/uwp/api/windows.graphics.capture.graphicscapturesession.minupdateinterval)). OBS measured WGC at **about 200-800 µs of CPU per frame**, against 300-500 µs for BitBlt, without stating the hardware ([62](https://github.com/obsproject/obs-studio/pull/2208)). At 30 fps that is roughly 0.6-2.4% of one core. OBS runs WGC with a two-buffer frame pool and copies each frame on the GPU ([63](https://raw.githubusercontent.com/obsproject/obs-studio/master/libobs-winrt/winrt-capture.cpp)). Desktop Duplication captures whole monitors only. It delivers frames only when "the operating system either updates the desktop bitmap image" or the pointer changes ([64](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_2/nf-dxgi1_2-idxgioutputduplication-acquirenextframe)), and it provides non-overlapping dirty rects plus move rects for scrolled or dragged regions ([65](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/desktop-dup-api)). Move rects map directly to RFB's CopyRect ([66](https://www.rfc-editor.org/rfc/rfc6143.html)). OS dirty regions can be too large, because toolkits redraw whole windows. TurboVNC's pixel compare exists to remove those false positives ([55](https://rawcdn.githack.com/TurboVNC/turbovnc/main/doc/index.html)).

The expensive steps are GPU-to-CPU readback and colour conversion. A 1080p readback measured **0.24-0.27 ms** on an RTX 2080 Ti. On an Intel HD 530 it measured 0.36 ms for an R8 surface and 2.36 ms for NV12, a 6.5x driver anomaly ([67](https://community.intel.com/t5/Graphics/NV12-copies-are-much-slower-than-similar-sized-resources/td-p/1156028)). Microsoft warns that a staging copy issued in frame N runs in frame N+1, so staging buffers must be double-buffered to avoid stalls ([68](https://msdn.microsoft.com/library/Bb205132(v=VS.85).aspx)). CPU SIMD conversion with libyuv AVX2 took about 0.25 ms per 720p frame ([69](https://chromium.googlesource.com/libyuv/libyuv/+/c5e45dcae58f5cb3eb893f8000c1de88a8fe3c4e)); scaled to 1080p that is roughly 0.6 ms. The Video Processor MFT does the same conversion on the GPU ([70](https://learn.microsoft.com/en-us/windows/win32/medfound/video-processor-mft)). NVENC accepts D3D textures and RGB input directly, and keeping data in video memory "avoids unnecessary PCIe transfers" ([71](https://docs.nvidia.com/video-technologies/video-codec-sdk/13.0/nvenc-video-encoder-api-prog-guide/index.html)). OBS 23 moved NVENC input from system RAM to VRAM to "noticeably reduce resource usage", but published no numbers ([72](https://obsproject.com/forum/threads/nvenc-performance-improvements-release-candidate.98950)). The one controlled recorder test, by LTT Labs, measured game frame-rate loss rather than CPU or RAM. Windows Game Bar, an all-GPU fixed-function path, cost **1 fps**; OBS cost 5-16 fps depending on GPU vendor ([73](https://gigazine.net/gsc_news/en/20260826-pc-screen-recorder/)). Memory needs are modest. The hybrid design keeps one previous frame, 8.3 MB at 1920x1080 BGRA (arithmetic), which matches TurboVNC's one framebuffer copy per viewer ([55](https://rawcdn.githack.com/TurboVNC/turbovnc/main/doc/index.html)). No published study measures the resident memory of any video encoder while it records screen content.

## Ranked conclusion: the best options for small, exact, light clips

**First: a change-driven hybrid tile coder with a lossless text path.** Capture the window with WGC as a GPU texture. Record only when frames arrive, using the QPC timestamps for variable frame rate. Take the OS dirty regions, confirm them with a tile compare against the previous frame, and turn moves into copy operations. Classify changed tiles by unique-colour count and by how often they change. Code few-colour UI and text tiles losslessly, with a palette or a spatial or previous-frame predictor followed by zstd at a low level or LZ4. Send only constantly changing many-colour tiles to a lossy coder, and refresh them losslessly once they go static. The design combines the largest measured lever (temporal redundancy, worth 4-40x), the cheapest proven classifiers (colour counts and timers), and the low-effort entropy setting that TurboVNC showed loses only about 10% for half the CPU. Idle cost is zero, and RAM is one frame copy. Its cost is a custom container that needs its own player or a transcode at export. Its evidence is the weakest of the top options: one desktop dataset plus protocol engineering documents, not a controlled study.

**Second: lossless inter-frame H.264 or HEVC in RGB/4:4:4, when a standard file is required at record time.** On a system with a Pascal-or-newer NVIDIA GPU, feeding WGC textures straight into NVENC lossless removes almost all CPU cost. The trade is size, which is roughly x264-ultrafast class or worse, and hardware decode of H.264 4:4:4 is doubtful, so HEVC 4:4:4 is the safer profile. Without NVENC, libx264rgb at qp 0 with a fast preset gives the best standard lossless ratio measured on screens (83-246:1), at much higher CPU cost.

**Third: a lossy codec with screen-content tools in 4:4:4 at constant quality, when "readable" is enough.** This route gives the smallest standard files: SCC saves 40-90% over non-SCC codecs on text and graphics. It does not give exact pixels. Practical real-time encoders expose only part of the tool set, and AV1's IntraBC is limited to keyframes. **Fourth: fast intra-only lossless codecs** (UtVideo, MagicYUV), only when CPU must be minimal and disk is cheap. **Avoid** full-screen 4:2:0 lossy video for text, lossless x265/AV1/VP9, lossless AVIF and JPEG-LS for screens, and high-effort entropy settings. Each of these loses on at least one of the three criteria with no offsetting gain in the evidence.

## OCR cannot certify text fidelity; pixel metrics on text crops can

OCR is a thresholded instrument. It reports no change until a glyph crosses a decision boundary, then jumps. In the one screen-recording encode sweep found, OCR errors stayed at **0-2 per 250 characters** across encodes while cropped SSIM fell from 0.971 to 0.849-0.883. Errors reached 7 only when letters visibly broke ([3](https://dev.to/yue_shu_c621a4a637f22396f/ocr-couldnt-tell-720p-lecture-text-from-1080p-a-cropped-ssim-could-4njo)). The instrument is also unstable at the other end. Small targeted perturbations flipped Tesseract 4 LSTM output with **79-97% success**, at an average L2 of about 3 on a [-1, 1] pixel scale ([74](https://ar5iv.labs.arxiv.org/html/1802.05385)). Tesseract output has differed between operating systems with the same Docker image ([75](https://harningle.github.io/2025/07/26/tesseract-inference-fine-tuning-and-reproducibility.html)). Its FAQ links inconsistent results to the adaptive classifier ([76](https://tesseract-ocr.github.io/tessdoc/FAQ.html)). Screen text sits near the engines' operating limits. Tesseract wants at least 300 DPI ([77](https://tesseract-ocr.github.io/tessdoc/ImproveQuality.html)), and the legacy Azure OCR needs 12 px text height at 1024x768 ([78](https://learn.microsoft.com/azure/ai-services/computer-vision/overview-ocr)). Typical UI text at 96 DPI falls below these figures, so codec changes land on OCR's most sensitive region. Engines also disagree sharply on screencast code: Tesseract "was never in the top three" of six engines ([79](https://www.researchgate.net/publication/342436852_A_Study_on_the_Accuracy_of_OCR_Engines_for_Source_Code_Transcription_from_Programming_Screencasts)). Windows.Media.Ocr returns words and boxes with no confidence values. Its model, determinism and minimum text size are undocumented, and it returns nothing for bitmaps that are too small ([80](https://learn.microsoft.com/en-us/uwp/api/windows.media.ocr.ocrengine), [81](https://docs.microsoft.com/en-us/answers/questions/692284/windowsmediaocr-won39t-scan-anything-if-width-ando-1.html)). The metric layer adds its own noise. WER can exceed 100%, segmentation errors multiply ([82](https://learn.microsoft.com/en-us/legal/cognitive-services/computer-vision/ocr-characteristics-and-limitations)), and different CER/WER implementations "yield different results" ([83](https://salford-repository.worktribe.com/output/1334107/a-survey-of-ocr-evaluation-tools-and-metrics)). Because most engines binarise or work on luminance, OCR is likely blind to the chroma-fringe loss that 4:2:0 causes. No source tests that directly.

The literature supports a different measurement stack. The primary test for any lossless or build-to-lossless path is **exact pixel equality** between the captured and decoded frames on static text regions, for example by hashing tiles. Any changed pixel is a defect, with no threshold to argue about. For lossy paths, use **full-reference metrics on fixed text crops**: luma SSIM or MS-SSIM and PSNR, plus a chroma error term, because coloured text loses most ([3](https://dev.to/yue_shu_c621a4a637f22396f/ocr-couldnt-tell-720p-lecture-text-from-1080p-a-cropped-ssim-could-4njo)). Fix and report the crop, since the same frame scored between 0.924 and 0.9993 depending on the crop. Screen-content quality research supports scoring text regions separately. SIQAD gives text regions their own subjective scores and finds that natural-image metrics often fail on thin, sharp-edged screen content ([84](https://ece.uwaterloo.ca/~z70wang/publications/QoMEX14b.pdf)). OCR remains useful in two narrow roles: as a pass/fail floor (text still machine-readable), and as a locator whose word boxes pick the text crops. When it is used, report ΔCER against the lossless source on the same machine, build and thread setting. Measure OCR's own noise floor first by re-reading the lossless frame under ±1 LSB noise. Aggregate over many frames with bootstrap confidence intervals. These recommendations are synthesised from the cited findings. No single source validates this stack end to end.

## Limitations

The largest limitation is the absence of a controlled benchmark of all families on real Windows application-window recordings. The top-ranked hybrid design rests on one self-reported desktop dataset with unpublished data and an unstated time unit ([1](https://ffmpeg.org/pipermail/ffmpeg-devel/2022-June/297402.html)), on emulator dumps ([5](https://tasvideos.org/Forum/Posts/302353)), and on protocol documentation that describes behaviour rather than measured numbers. Much of the lossless-codec evidence comes from forums using natural video, one machine and often one clip. The strongest peer-reviewed numbers (HEVC/VVC SCC BD-rates) come from reference encoders that cannot run in real time, and they measure PSNR, not text legibility. No published study measures the RAM use of any video encoder on screen content, or CPU use of hardware encoders on Windows desktop recording. Several key facts are undocumented. The exactness of NVENC's RGB-to-YUV step in lossless mode is unknown. The semantics of WGC's `MinUpdateInterval` and `DirtyRegionMode` are unknown, as is whether WGC suppresses frames for unchanged windows. Hardware support for Intel SCC varies by CPU generation. On OCR, no study gives the flip rate under random small noise or chroma subsampling alone, no CER-versus-QP curve exists for screen text, and ClearType rendering has not been isolated. Vendor claims, such as ScreenPressor's 300x and NVIDIA's OBS figures, are reported but not relied on.

## Conclusion

The question "which codec?" turns out to be the wrong unit of analysis for screen recording. The literature says the decisive choices are architectural. They are: code only what changed; route text and UI through a lossless palette-or-predictor path; spend lossy bits only where pixels churn; and keep frames on the GPU until they are coded. Remote-display engineering solved this problem a decade ago under bandwidth pressure. A clip recorder faces the same problem under disk and CPU pressure, and it can adopt the same answer, because nothing in the transferable techniques depends on drawing-command remoting. What has not been done is to measure that answer properly. The next step is a local bake-off on real window recordings, using the QOI screenshot suite and LSCD ([85](https://arxiv.org/abs/2308.09332)) as public anchors and exact-pixel equality plus cropped full-reference metrics as the scoring rule, not OCR. That bake-off should test the hybrid design against NVENC HEVC 4:4:4 lossless and libx264rgb qp 0. It will settle whether the single 112:1 data point generalises.
